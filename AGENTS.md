# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Tests split into `tests/unit` (deterministic, no network, `pytest tests/unit`) and `tests/eval` (real LLM behavior, gated by `ANTHROPIC_API_KEY`, `pytest -m eval`). See `docs/TESTING.md` for the full test-case catalog and the TDD workflow (write test first).
- `pytest -m eval` needs the `web` extra installed to collect cleanly — install with `.[anthropic,embed-local,vec,web,dev]` (add `youtube` too if touching YouTube ingest).
- YouTube ingest (`distil/youtube.py`) shells out to `yt-dlp` via an injectable `run` callable so unit tests fake the subprocess boundary — never invoke the real binary in `tests/unit`. When fetching captions, use `--sub-langs en` (exact match), not a wildcard like `en.*`: the wildcard also matches yt-dlp's auto-*translated* variants (`en-de`, `en-fr`, ...), which are lower quality and can outrank the real English track once sorted.
- **YouTube fetch hardening (Phase 19).** Both `yt-dlp` call sites (`list_playlist_video_urls`, `_fetch_into`) pin `--extractor-args "youtube:player_client=android,web"`: `android` isn't throttled nearly as hard as the default `web` client on datacenter/container egress IPs (429s), and unlike `web` it needs no JS interpreter to solve YouTube's n-parameter signature challenge — which matters because `python:3.11-slim` (the Dockerfile base) has no JS runtime installed, hence the harmless "No supported JavaScript runtime" warning if `web` is ever used alone. `web` stays as a same-call fallback for the rare video whose `android` response lacks captions. Both sites also retry through `_run_yt_dlp` (injectable `sleep`, same DI pattern as `run`) on transient failures (429/5xx/network, matched via `_is_transient_failure`) with bounded exponential backoff (`_TRANSIENT_MAX_ATTEMPTS`/`_TRANSIENT_BASE_DELAY`) before raising `YoutubeFetchError`; a persistent block still fails fast. Do not add a JS runtime (deno/node) to the image to chase a different client chain without checking whether `android`/`web` still avoids that need — it was a deliberate choice to keep the image slim.
- Fetched YouTube captions are converted to `.srt` and parsed with `distil.ingest.ingest_srt_text`, so downstream stages never know the source was YouTube rather than an uploaded file.
- Alongside `kb/<id>.md` (lossless JSON, internal source of truth), `distil/okf.py` derives a neutral per-video [OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog) bundle (`okf/sources/<slug>.md` + `okf/raw/<slug>.md` + `okf/concepts/<concept_id>.md` + indexes) with no feedback/application-link data. `distil/okf_lint.py` (stdlib only, `python -m distil.okf_lint <okf_root>`) validates it end to end, including E5-E8 for `concepts/` (frontmatter+index coverage, concept<->source citation integrity, bidirectional links, no-orphan-concepts). `Store.file_entry(..., transcript=...)` triggers the source/raw export; omit `transcript` for feedback-only re-files to leave OKF pages untouched. Slug = stable slugified `source.title` (falls back to `entry_id`) via `okf.slugify`. `entities/` layers and OpenKnowledge wiring are later phases — not implemented yet.
- **Concept synthesis (OKF Phase 3a, Phases 15.1-15.3) is fully wired and on by default.** Per filed video: `distil/canonicalize.py`'s `canonicalize_entry(entry, store, client)` decides match/new/reject per knowledge item against the `concepts` SQLite table (the `graph.py` deterministic-candidates-then-capped-LLM-call shape, at item granularity, with embedding similarity — `Store.find_concept_candidates` — as the primary candidacy signal; idempotent via `Store.retract_entry_concept_memberships`, run before every re-canonicalize and on `delete_entry`); `synthesize_touched_concepts(...)` (`distil/synthesize_concept.py`) then (re-)writes prose for touched concepts, reusing `note.py`'s grounded-claim discipline — every `ConceptClaim.item_ids` must resolve to a real member, citations are code-assembled (`render_claim`) from verified member/entry data, never model-authored — capped at `MAX_CONCEPTS_TO_SYNTHESIZE_PER_VIDEO` (env `DISTIL_CONCEPTS_SYNTH_PER_VIDEO`, default 5), with overflow marked `Concept.pending_synthesis=True` for a later catch-up pass (Phase 17's `sync-pending` CLI, not built yet). `canonicalize.run_canonicalize_stage(entry, store, client)` is the one orchestration entry point that also talks to `okf.py` (`export_concept`/`remove_concept`/`render_source_with_concepts`) and is what `pipeline.run_pipeline`'s Stage 8 calls, gated by `PipelineConfig.enable_canonicalize` (default `True`, mirrors `enable_graph`) — it also re-exports/removes concepts that lost this entry as a member (not just ones it touched), which is what keeps lint's E7 bidirectional-link check passing after a re-file changes membership. `CONCEPT_SIM_FLOOR` (0.55) / `MAX_CONCEPT_CANDIDATES` (5) in `store.py` (env `DISTIL_CONCEPT_SIM_FLOOR`/`DISTIL_CONCEPT_MAX_CANDIDATES`) passed the §6 validation gate (`tests/eval/test_canonicalize_eval.py`, `pytest -m eval`) unchanged on a real-model paraphrase-clustering fixture (3/3 runs, gate-produced bundle lints clean) — no retune was needed before shipping the default on. `okf.py` and `synthesize_concept.py` avoid importing `store.py` at runtime to prevent an `okf <-> store` import cycle (`store.py` imports `okf.py`) — both use `if TYPE_CHECKING: from .store import Store` for the type hint only, calling `store.*` methods duck-typed at runtime. Not yet built: concept<->concept typed edges/contradiction flags (Phase 16), `distil concepts merge/split/sync-pending` (Phase 17). See `distil-phase3-design/report.md` (kept outside this repo) for the full design rationale.
- **Query-over-concepts (OKF Phase 3d / Phase 18) is wired into the one shared read path.** `distil/query.py`'s `retrieve_concepts(question, store, embedder)` ranks `Store.list_concepts()` against the question the same way `retrieve()` ranks raw items, scoring each concept as the *better* of its stored centroid's cosine similarity (`Store.concept_centroid`) and any single member item's similarity (`Store.iter_item_vectors`) — blending in members so a concept isn't hidden behind a centroid diluted by loosely-related videos. `ask()`/`stream_ask()` (the only functions the CLI `ask` command and `web/app.py`'s `/ask`+`/ask/stream` routes call) gate concepts through the exact same `threshold` as items — abstention only fires when *neither* clears it — then blend each cleared concept's member items into the evidence pool (`_recruit_concept_members`, resolved fresh from the live `KBEntry`, never from the concept's own copied `quote`/`timestamp`) and append its already-grounded `ConceptClaim` prose as extra synthesis context (`_render_concept_notes`); citations are still validated against the full recruited-item set post-synthesis, so the faithfulness guarantee (T-Q2/T-Q3) is unchanged. Concepts are strictly a consumer of item-level retrieval, never a substitute for it.
