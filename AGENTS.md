# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Tests split into `tests/unit` (deterministic, no network, `pytest tests/unit`) and `tests/eval` (real LLM behavior, gated by `ANTHROPIC_API_KEY`, `pytest -m eval`). See `docs/TESTING.md` for the full test-case catalog and the TDD workflow (write test first).
- `pytest -m eval` needs the `web` extra installed to collect cleanly — install with `.[anthropic,embed-local,vec,web,dev]` (add `youtube` too if touching YouTube ingest).
- YouTube ingest (`distil/youtube.py`) shells out to `yt-dlp` via an injectable `run` callable so unit tests fake the subprocess boundary — never invoke the real binary in `tests/unit`. When fetching captions, use `--sub-langs en` (exact match), not a wildcard like `en.*`: the wildcard also matches yt-dlp's auto-*translated* variants (`en-de`, `en-fr`, ...), which are lower quality and can outrank the real English track once sorted.
- **YouTube fetch hardening (Phase 19; client chain replaced in Phase 21).** Both `yt-dlp` call sites (`list_playlist_video_urls`, `_fetch_into`) pin a player-client chain via `--extractor-args` and retry through `_run_yt_dlp` (injectable `sleep`, same DI pattern as `run`) on transient failures (429/5xx/network, matched via `_is_transient_failure`) with bounded exponential backoff before raising `YoutubeFetchError`. See `distil/youtube.py`'s module docstring for the current chain and why — it's re-derived from yt-dlp's own `_DEFAULT_CLIENTS`/`_DEFAULT_JSLESS_CLIENTS` (`yt_dlp.extractor.youtube._video`) periodically as yt-dlp changes its recommendations, so treat the docstring as the source of truth rather than this bullet. Do not add a JS runtime (deno/node) to the image to chase a different client chain without checking whether the current no-JS default already avoids that need — it was a deliberate choice to keep the image slim.
- **Real yt-dlp errors, not warnings, must reach users (Phase 21).** Both call sites pass `--no-update` (suppresses yt-dlp's own "N days old" staleness warning) and route failures through `_surface_error`, which prefers yt-dlp's `ERROR:`-prefixed line(s) over anything else in stderr and falls back to a genuine tail (last N chars) otherwise. Never reintroduce a head-truncating `stderr[:limit]` helper here — that exact bug (a since-removed `_tail`) once hid every real failure behind warning noise (SABR-format / staleness warnings) for months. The complete, untruncated stderr is always logged via the standard `logging` module (`logging.getLogger(__name__)` — this is the repo's only logging convention so far); only the raised exception's message is bounded.
- **Caption format: `srt` natively, never `--convert-subs` (Phase 21).** `_fetch_into` requests `--sub-format srt/best` and nothing else — no `--convert-subs`. YouTube's timedtext endpoint serves `srt` directly for both manual and auto-generated tracks. This matters because the Dockerfile image has no ffmpeg installed, and yt-dlp's subtitle-conversion postprocessor shells out to ffmpeg for every format except ttml/dfxp — the previous `json3` + `--convert-subs srt` combination could never have worked in production (ffmpeg can't even parse json3 as an input format) and was the actual root cause behind a "yt-dlp failed" report that a stderr-truncation bug (see above) had been hiding. If a future caption need reintroduces `--convert-subs`, verify ffmpeg is actually installed first, or accept ttml/dfxp as the only ffmpeg-free conversion path.
- **PO-token provider, not a YouTube API key (Phase 22; supersedes the removed Phase 20 `DISTIL_YOUTUBE_API_KEY`).** The Railway failure ("Sign in to confirm you're not a bot") is a bot-identity challenge on a datacenter IP, not a rate limit — `DISTIL_YOUTUBE_API_KEY`'s `innertube_host`/`innertube_key` substitution never carried any identity and could not have addressed it (confirmed against installed yt-dlp source before removal); it has been deleted, not deprecated. The real fix is a PO (proof-of-origin) token from a real attestation provider: when `DISTIL_POT_PROVIDER_URL` is set, `_extractor_args()` (`distil/youtube.py`, read at call time, shared by both `yt-dlp` call sites) appends a *second* `--extractor-args` pair, `youtubepot-bgutilhttp:base_url=<url>` — its own extractor namespace, never suffixed onto the `youtube:` value — pointing yt-dlp's `bgutil-ytdlp-pot-provider` plugin (installed via the `youtube` extra; pure Python, no Node/Deno needed in this image) at a separately-run `bgutil-ytdlp-pot-provider` HTTP server (a second Railway service; see DEPLOY_RAILWAY.md). Absent the env var, the command line is byte-identical to before. Per upstream's own docs, a PO token makes traffic look more legitimate — it does **not** guarantee clearing a bot check, and that outcome can only be confirmed on the actual datacenter deploy, never from a residential dev machine.
- **A discovered-and-loaded provider is not the same as a provider actually asked for a token (Phase 23).** Phase 22's wiring worked once and then silently stopped asking for most videos: yt-dlp's default `fetch_pot=auto` policy skips the provider entirely for any (client, context) pair whose static PO-token policy doesn't mark it required/recommended, and `web_safari` — being yt-dlp's own `_DEFAULT_WEBPAGE_CLIENT` — never even makes a dedicated Innertube player call to attach a token to in the first place (it reuses the watch-page's embedded response). Fixed by folding `fetch_pot=always` into the `youtube:` extractor-args value (only when `DISTIL_POT_PROVIDER_URL` is set — never as a separate `--extractor-args` pair, since yt-dlp *replaces* rather than merges repeated args for one extractor) and adding `mweb` as a third-tier client — the only chain member that's both PO-token-eligible and never a webpage client. See `distil/youtube.py`'s module docstring for the full, source-verified reasoning; don't re-derive it from scratch. **Never trust "the plugin loaded" alone as proof the fix works** — `distil youtube-diagnose-pot <url>` (CLI) or `GET /diagnostics/youtube-pot?url=...` (web, auth-gated) is the permanent, reusable way to check both the `PO Token Providers:` discovery line *and* which `(context, client)` pairs a fetch actually attempted, without shell access to the container. An empty attempt list with a healthy discovery line means the same "never asked" class of bug as this phase — check that before assuming the bot check itself is unbeatable.
- Fetched YouTube captions are parsed with `distil.ingest.ingest_srt_text`, so downstream stages never know the source was YouTube rather than an uploaded `.srt` file.
- **Extraction robustness (`distil/extract.py`)**: a long transcript can hit the 4,096-token output cap, or the connection can drop — both truncate the model's JSON array response identically. `run_extraction` → `_complete_with_retry` retries the model call (bounded `_MAX_RETRIES`, short sleep) on exactly that failure mode (network exception, or `_parse_items_json` can't recover a usable array); a schema-level failure in an item that *did* fully parse happens later in `_items_from_json` and is never retried. `_parse_items_json` falls back to `_recover_truncated_leading_objects` when the response is a `[`-prefixed array that was never closed: it decodes whatever complete leading objects it can and discards the truncated tail, never fabricating a partial item — reject (`ParseError`) only when nothing at all recovers. `FakeClient.complete` (`distil/llm.py`) accepts queued `Exception` instances (raised instead of returned) to let tests simulate a dropped connection ahead of a successful retry. **`type`/`stance` drift (T-E8)**: `KnowledgeType` and `Stance` (`distil/models.py`) share near-synonym vocabulary (`experiential` vs `personal_experience`) and the model sometimes copies a `stance` value into `type`. `_items_from_json(data, requested_type)` repairs an invalid `type` to the type `build_extract_prompt` was called with (the caller always knows the one correct value for that call) via `_repair_type`; a `type` that's a *different but still valid* `KnowledgeType` is left alone. An item that still fails validation after repair is dropped (logged), not fatal for the batch, unless fewer than `_MIN_SALVAGE_FRACTION` (50%) of items survive, in which case it still raises `ParseError` — a floor against silently returning a near-empty result from a wholesale-broken response.
- Alongside `kb/<id>.md` (lossless JSON, internal source of truth), `distil/okf.py` derives a neutral per-video [OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog) bundle (`okf/sources/<slug>.md` + `okf/raw/<slug>.md` + `okf/concepts/<concept_id>.md` + `okf/entities/<entity_id>.md` + indexes) with no feedback/application-link data. `distil/okf_lint.py` (stdlib only, `python -m distil.okf_lint <okf_root>`) validates it end to end, including E5-E8 for `concepts/` and E9-E12 for `entities/` (frontmatter+index coverage, citation integrity, bidirectional links, no-orphans). `Store.file_entry(..., transcript=...)` triggers the source/raw export; omit `transcript` for feedback-only re-files to leave OKF pages untouched. Slug = stable slugified `source.title` (falls back to `entry_id`) via `okf.slugify`. OpenKnowledge wiring proper is a later phase — not implemented yet.

- **Concept layer surfaced in the web app (Phase B).** `web/app.py` reads `store.list_concepts()`/`load_concept()` directly (never regenerates OKF pages — read-only over the bundle): `/concepts` (list, client-side filter+sort mirroring `library.html`'s pattern — deliberately no A-Z letter-bar index, since the filter box strictly dominates it) and `/concepts/{concept_id}` (claims with citations resolved to `/entries/{id}#{item_id}`, deduped sources, typed edges grouped by relation, and the same `synthesize_concept.find_claim_contradictions` deterministic flag `okf._render_concept` already uses). Entry pages link to `/entries/{id}/transcript.md` (reads `okf_root/raw/<slug>.md` via `okf.slug_for_entry`, mirroring the `teaching-note.md` route) and to concepts that entry contributed to. `/bundle.zip` streams the whole `okf_root` as a zip via `_ZipChunkBuffer` (a `zipfile.ZipFile`-writable buffer drained after each file so the archive is never fully built in memory) — every route above degrades to an empty state/404, never an error, when `okf_root` or a given bundle file doesn't exist yet (fresh deploy, or an entry filed without `transcript=`). All new routes ride the existing `_auth_gate` middleware for free (it gates every path except `/health`/`/login`/`/static`) — no route-level auth code needed.
- **Visible per-stage progress (Phase A) replaces the old static "Extracting items..." string.** `PipelineConfig.phase_callback` (`distil/pipeline.py`) is `_timed`'s new sibling to `timing_callback`: it fires `(stage, "start")` before and `(stage, "finish")` after every stage `_timed` wraps — this is the single hook point, so no stage-body code sprinkles progress calls (the `("<stage>", "short_circuit")` event mentioned below is emitted by *callers* of `run_pipeline`, not by `run_pipeline` itself — see the "Triage no longer gates the pipeline" entry). `distil.youtube.fetch_video_transcript`/`_fetch_into` take the same-shaped `on_phase` callback (default `None`, behavior-preserving) around the yt-dlp subprocess (`transcript_fetch`) and the srt parse (`caption_parse`) — the two slowest, most failure-prone steps, which sit outside `run_pipeline`. `web/app.py`'s `_PhaseReporter` is the one place these events become durable state: `_build_phase_plan(job, ...)` computes the ordered phase list *for this job* from its kind (youtube gets `transcript_fetch`+`caption_parse`; paste/file get `ingest`) and the enabled-stage flags (so the declared total never claims a stage that won't run), then `web/jobs.py`'s `JobStore.start_phase`/`record_phase_duration`/`collapse_total` persist current phase/index/total/started-at and a `phase_durations` JSON blob on the job row. `collapse_total` is what makes an early-exit report honest — it shrinks `phase_total` down to whatever `phase_index` already reached instead of leaving the UI claiming a total the run will never hit. A failed job's `current_phase` is deliberately never cleared on failure, so "which phase it failed in" is just whatever phase last called `start_phase`. `web/templates/index.html`'s existing 2s `/jobs` poll renders `current_phase`/`phase_index`/`phase_total`/`phase_started_at` into "Step N of M · <label> · Ns"; `web/templates/entry.html` renders the persisted `phase_durations` (via `JobStore.find_by_entry_id`) as a collapsed `<details>` breakdown on the entry page. No new dependency, poller, or websocket was added.
- **Triage no longer gates the pipeline; the only rejection is a word count, enforced at ingest (owner decision, supersedes the old `little_to_extract` short-circuit).** The owner: "If I have given a note or a YouTube video, my judgment has to be trusted, and it is a go unless the transcript is not available. If the transcript has less than 50 words, it should be rejected." `distil/pipeline.py`'s `run_pipeline` no longer has any short-circuit — it always runs triage+extract (merged, see the next entry) → normalize → link → note → (graph) → file → (canonicalize → concept edges) and files the result; `triage.verdict` is stored (other code/data depend on its shape — `distil/store.py`'s rendering, `distil/cli.py`, `web/app.py`'s summaries) but nothing acts on it, only `knowledge_types_present` (routes `extract.py`), `density`, and `transcript_loss` matter downstream. The word-count gate lives in `distil/ingest.py` instead: `_check_min_words` runs at the tail of `_parse_srt` and `ingest_text` — the two low-level parsers every public entry point (`ingest_file`, `ingest_text`, `ingest_srt_text`) bottoms out in — so it covers all four ingest paths (paste, upload, YouTube fetch via `youtube.ingest_srt_text`, external-collector submit) from two call sites, raising `TranscriptTooShortError` (an `IngestError` subclass, `MIN_TRANSCRIPT_WORDS`=50, env `DISTIL_MIN_TRANSCRIPT_WORDS`). `distil/youtube.py`'s `_fetch_into` re-raises it unwrapped rather than folding it into `YoutubeFetchError`, so a too-short fetch is never confused with a real fetch failure. Every caller that can hit this exception treats it as a clean, distinct rejection — never `STATUS_FAILED`: `web/app.py`'s `_distill_job` (paste/file/single-video), `_fetch_playlist_video` (playlist prefetch), and `collector_submit_transcript` (external collector) all map it to `web/jobs.py`'s `STATUS_LOW_VALUE` (now exclusively this meaning; badge text "Too short"), and `distil/cli.py`'s `run` command prints the message directly. `Store.list_entries()` had a latent trap for this change: it used to prune any indexed row whose loaded entry had `verdict == "little_to_extract" and not knowledge_items` — now a completely normal, expected shape — which would have silently deleted freshly-filed entries the moment the library was listed; that pruning was removed, and only a row whose backing `kb/` file is actually missing gets pruned. **Thin-material visibility (not a second rejection rule):** a word count can't detect a fetch that died partway through a long video, and `Source.duration_sec` is never populated (would require touching yt-dlp fetch machinery, out of scope here) — so `Source.transcript_word_count` (set once in `pipeline.py` from the final transcript) backs a separate, higher, non-gating threshold, `ingest.is_thin_source`/`THIN_TRANSCRIPT_WORDS`=500 (env `DISTIL_THIN_TRANSCRIPT_WORDS`; `0` means unknown/pre-existing and is never flagged). It surfaces as a "thin source" badge on `web/templates/entry.html` and a "Thin material" line in `store.py`'s rendered markdown/teaching-note export — visible, never rejected.
- **Triage and extraction are merged into one strong-tier call; the narrative summary runs concurrently with it, starting at the front (owner decision, same task as the previous entry — folded in to avoid a second validation run on the same function).** The old two-call design (a cheap classification pass, then extraction) existed only so the classification could veto extraction before it ran — the previous entry's short-circuit removal means that veto is gone, so reading the transcript twice bought nothing anymore. `extract.run_triage_extract` (`distil/extract.py`) is the merged call `pipeline.run_pipeline` now uses in place of separate `triage.run_triage`/`extract.run_extraction` calls: one `client.complete` against `prompts/triage_extract.py`'s two-section prompt, which asks the model to emit a `<TRIAGE>...</TRIAGE>` classification FIRST and an `<ITEMS>...</ITEMS>` array SECOND, conditioned on it — decide-then-act preserved via response ordering within one call rather than via two separate calls. Parsing deliberately keeps both pre-existing, separately-tested parsers rather than inventing one for a merged JSON object: `triage.parse_triage_response` (renamed from the old private `_parse`, now also called directly by `run_triage` — same function, two callers) on the `<TRIAGE>` text, and `extract._parse_items_json` (with its existing truncated-array recovery, unchanged) on the `<ITEMS>` text — `extract._split_triage_extract_response` finds the tags and is tolerant of truncation only in `<ITEMS>` (a long items array can hit the output-token cap; the small `<TRIAGE>` object is not expected to). `triage.py`'s own `run_triage`/`TriageResult` are NOT deleted — they remain a standalone, independently-testable classifier for the gated eval suite (`tests/eval/test_triage_eval.py`) and any future diagnostic use, just no longer on the pipeline's call path. `model_config.STRONG_TIER_STAGES` dropped `"triage"` (it resolves as `"extract"` now); `run_pipeline` dropped the `triage_client` kwarg PR #26 had added (no caller used it yet, and there is no longer a separate stage to inject a client for). **Concurrency (addendum Part 2 — supersedes an initial "runs after note" placement from the same task):** the narrative summary must start at the front (the owner sees a readable account sooner, and it survives a later extraction failure instead of dying behind it) but must not block extraction (they share no data — both only read the transcript). `run_pipeline` starts a plain daemon `threading.Thread` (stdlib, no new dependency) running `_SummaryRun.execute` immediately after computing `source`/`meta`, fires `phase_callback("narrative_summary", "start")` at that same point, then proceeds synchronously through the merged extract call, normalize, link, and note exactly as before. Only once `entry` exists does it call `_join_narrative_summary`, which does `thread.join(timeout=...)` bounded by `DISTIL_SUMMARY_JOIN_TIMEOUT_SECONDS` (default 60s) — in the common case the summary already finished during the other stages, so this costs nothing; a summary still running past the bound is abandoned (`thread.is_alive()` after the bounded join says so) and logged as a warning naming the bound, exactly as honestly as an in-stage failure is already logged — `entry.narrative_summary` stays `None` either way, never a silent absence, and the owner's existing refresh action can always generate it later. Deliberately a plain daemon thread, not `concurrent.futures.ThreadPoolExecutor`: that class registers an `atexit` hook that blocks interpreter shutdown until every worker thread finishes, even after `shutdown(wait=False)` — for the one-shot CLI (`distil run`), that would mean process exit silently hangs waiting for an abandoned, already-timed-out-and-ignored summary call, defeating the entire point of the bound. A daemon thread is simply killed when the process exits, with no such wait. All `phase_callback`/`timing_callback` invocations — including the delayed "finish" for `narrative_summary` — still happen only on the main thread (never from the background thread), so no cross-thread sqlite-write concern was introduced into `web/jobs.py`'s `_PhaseReporter`; `web/app.py`'s `_build_phase_plan` lists `narrative_summary` right after `metadata`, before `extract`, matching where its "start" event actually fires (a phase's declared index only ever advances on a "start" event, so its belated "finish" doesn't disturb the displayed step count). An extraction failure and a summary failure/timeout are independent and never mask each other: extraction's exception still propagates out of `run_pipeline` unconditionally (the summary thread is simply abandoned, not awaited, when that happens), and a summary failure never touches `entry.knowledge_items`/anything else. **Not independently verified in this environment:** the addendum also asked for a live extraction-quality comparison against the old split-call path, and a real ingest cost measurement — both need `ANTHROPIC_API_KEY`, which was not available in the authoring environment; `tests/eval/test_triage_extract_merge_eval.py` is written and gated for whenever real credentials are available, but was not executed, and no cost number is claimed.
- **Query-over-concepts (OKF Phase 3d / Phase 18) is wired into the one shared read path.** `distil/query.py`'s `retrieve_concepts(question, store, embedder)` ranks `Store.list_concepts()` against the question the same way `retrieve()` ranks raw items, scoring each concept as the *better* of its stored centroid's cosine similarity (`Store.concept_centroid`) and any single member item's similarity (`Store.iter_item_vectors`) — blending in members so a concept isn't hidden behind a centroid diluted by loosely-related videos. `ask()`/`stream_ask()` (the only functions the CLI `ask` command and `web/app.py`'s `/ask`+`/ask/stream` routes call) gate concepts through the exact same `threshold` as items — abstention only fires when *neither* clears it — then blend each cleared concept's member items into the evidence pool (`_recruit_concept_members`, resolved fresh from the live `KBEntry`, never from the concept's own copied `quote`/`timestamp`) and append its already-grounded `ConceptClaim` prose as extra synthesis context (`_render_concept_notes`); citations are still validated against the full recruited-item set post-synthesis, so the faithfulness guarantee (T-Q2/T-Q3) is unchanged. Concepts are strictly a consumer of item-level retrieval, never a substitute for it.

- **Answer depth (Phase C) — concept pages surfaced beside an answer, whole-page content optionally reaching synthesis.** `AskResult.concepts` (`ConceptRef(concept_id, title)`) is populated for free from `cleared_concepts` — the same list the gate already computed — in both `ask()` and `stream_ask()`'s final event; `web/app.py`'s `_ask_payload` (the one function both the `/ask` route and `/ask/stream`'s final SSE event call) serializes it, and `web/templates/index.html` renders it as `<a class="badge info" href="/concepts/{id}">` links next to the existing sources list, reusing the concept detail route from the preceding phase rather than duplicating it. Zero extra retrieval or model calls. Separately, `_render_concept_notes(concepts, store, *, depth)` controls how much of a matched concept's *own* substance reaches the synthesis prompt: `"claims"` (default) sends each `ConceptClaim.text` plus its `[item_id]` markers, unchanged from Phase 18; `"full"` additionally inlines each cited member's real `ConceptMember.quote` beneath its claim (still scoped to `concept.members`/`concept.claims` only — no edge traversal). Resolved once per call via `_resolve_concept_note_depth`: an explicit `concept_note_depth` kwarg wins, else `DISTIL_CONCEPT_NOTE_DEPTH` env (read at call time, same pattern as `DISTIL_CONCEPT_SIM_FLOOR`), else `CONCEPT_NOTE_DEPTH_DEFAULT`; an unrecognized value degrades to the default rather than raising. Default is `"claims"`, not `"full"`, measured deliberately: on a realistic 3-claim/6-quote concept fixture, `"full"` cost ~3.2x the tokens of `"claims"` (+266 est. tokens, ~3.7 chars/token) for content that's largely already present in the evidence pool anyway — every cleared concept's member items are unconditionally recruited into `all_items`/`_render_notes` (Phase 18) regardless of this setting, so `"full"` mostly buys claim-to-quote structural linkage, not new grounding facts. The relevance gate and post-synthesis citation validation are untouched by any of this — both operate exactly as in Phase 18 regardless of `concepts`/depth.
- **Delete cascade and OKF reconcile (post Phase 18).** `Store.delete_entry` is pure DB/file-store (kb file, index row, vectors, membership retraction) and never touches the OKF bundle — `canonicalize.run_delete_entry_stage(entry_id, store)` is the one orchestration entry point that does, mirroring `run_canonicalize_stage`'s role on the file path: it resolves the entry's OKF slug *before* calling `delete_entry` (which deletes the kb file a normal slug lookup needs), falling back to `okf.find_slug_for_entry_id` (a search over `sources/*.md`'s own `distil_entry_id` frontmatter) when the kb file is already missing or unparseable, then removes that entry's `sources/`/`raw/` pages and either re-exports or removes every concept the entry was a member of. Both the CLI `delete` command and `web/app.py`'s `/entries/{id}/delete` route call this, never `store.delete_entry` directly. `distil/reconcile.py`'s `reconcile_okf_bundle(store, apply=...)` (CLI: `distil reconcile [--apply]`, dry-run by default) repairs a bundle that already drifted — orphaned `concepts/`/`sources/`/`raw/` pages with no live DB owner — and is conservative by construction: a `sources/` page with missing/unparseable `distil_entry_id`, or a `raw/` page with no matching `sources/` page, is reported as skipped rather than guessed at and deleted. It never touches `kb/` or the database, only the derived `okf/` bundle.

- **Playlist up-front fetch + persistent staging (Phase E).** A playlist's transcripts are fetched before distilling starts, not one-at-a-time interleaved with distilling — `web/jobs.py` gained a second single-worker background thread, `Fetcher`, claiming a `STATUS_PENDING_FETCH`/`STATUS_FETCHING` pair that's disjoint from the distill `Worker`'s `queued`/`running`, so the two never contend for the same job and genuinely overlap (the distill Worker can process video 1 while `Fetcher` is still fetching video 3). `_enqueue_youtube_source` (`web/app.py`) enqueues a playlist's jobs directly into `STATUS_PENDING_FETCH` (a single-video submission is unchanged: still `queued`, still fetched inline at distill time via `_load_job_transcript`'s `kind=="youtube"` branch — only playlists batch). `Fetcher.process_once()` pauses `delay_seconds` (env `DISTIL_PLAYLIST_FETCH_DELAY_SECONDS`, default 3.0, injectable `sleep` for tests) before every fetch after the first, never before the first. `_fetch_playlist_video` calls the unmodified `youtube.fetch_video_transcript` (same `on_phase` reporting, same retry/error surfacing — `distil/youtube.py` itself is untouched) and, on success, `_stage_transcript` writes the parsed `Transcript` as JSON under `_transcript_stage_dir()`, then `JobStore.mark_fetched` flips the job to `queued` with `kind=KIND_YOUTUBE_STAGED`; from there the distill Worker's `_load_job_transcript` reads it back via `_load_staged_transcript` exactly like an uploaded file — but, unlike before, reading no longer deletes it (a missing file raises an honest `FileNotFoundError` instead). Cleanup is reclassified by outcome, not by read: `Worker`'s optional `on_finished(job)` hook (`web/app.py` wires it to `_cleanup_staged_file`) fires only once a job reaches a *successful* terminal status (done/low_value) — a downstream pipeline failure after the read leaves the staged file in place so `JobStore.retry()` can still re-read it on the next attempt. A fetch failure (no captions, bot check, timeout) marks only that job `failed` with a readable error — `recover_interrupted` (jobs.py) now recovers both a crashed `running` job (`-> queued`) and a crashed `fetching` job (`-> pending_fetch`) in one call, and since nothing unlinks a staged file except a successful finish, a recovered `youtube_staged` job still finds it on disk. **Same pass fixed a live latent bug this change would otherwise have inherited**: staged content (uploads, and now prefetched transcripts) used to live under `tempfile.gettempdir()` — wiped by a container restart/redeploy even though the job row (sqlite, on the volume) survives. `_staging_root()` now derives from `DISTIL_DB_PATH`'s own directory by default (override via `DISTIL_STAGING_DIR`), so `_upload_dir()`/`_transcript_stage_dir()` land on the same persistent volume as the db/kb; staged files are also cleaned up on `POST /jobs/{id}/remove` and `POST /jobs/clear`, and — since a permanently-failed job's file would otherwise be kept forever for a retry that never comes — `JobStore.autoclear`'s optional `on_stale_failed(job)` hook reaps a `failed` job's staged file once it has sat untouched past the same 24h bound `autoclear` already uses for finished rows (the row itself persists; only the file is reclaimed), so this doesn't trade the data-loss bug for unbounded volume growth. `web/templates/index.html`'s Activity view got `pending_fetch`("Waiting to fetch")/`fetching`(spinner + real phase progress, same `progressDetail` as `running`) so a playlist's up-front fetch reads honestly instead of looking like one stalled job.
- **Entities layer (Phase D) is fully wired and on by default, and rides the existing extraction call — zero new transcript reads, zero new pipeline stages.** `EntityKind` (`distil/models.py`) is a closed 3-way enum (`tool`/`person`/`organization`), deliberately kept separate from `KnowledgeType`/`Stance` in the extraction prompt (`distil/prompts/extract.py`) after the T-E8 `type`/`stance` conflation incident — the system prompt spells out all three vocabularies are never interchangeable. Each `KnowledgeItem` carries its own `entity_mentions: list[EntityMention]` (name/kind/description/quote/timestamp), extracted alongside it in the *same* JSON array element rather than a separate top-level array or a second call. `extract._clean_entity_mentions` validates/drops each mention *before* the parent item is ever constructed (mirrors `_repair_type`'s "fix what's recoverable" shape but per-mention, with no repair-and-guess for `kind` — an untrustworthy kind is dropped, not coerced) — this is what makes a malformed entity structurally incapable of failing (and thereby dropping) its knowledge item; entities have no salvage floor of their own since they're optional per item. `distil/canonicalize.py` extends Stage 8 (not a new stage): `canonicalize_entry_entities`/`synthesize_touched_entities` are the exact `canonicalize_entry`/`synthesize_touched_concepts` shape one granularity down (mentions instead of items), with `Store.find_entity_candidates` adding a hard `kind` pre-filter concepts don't have on top of the same embedding-similarity + token-overlap candidate pool; capped at `MAX_ENTITIES_TO_SYNTHESIZE_PER_VIDEO` (env `DISTIL_ENTITIES_SYNTH_PER_VIDEO`, default 5) with overflow marked `pending_synthesis`, same catch-up-later discipline as concepts. `synthesize_concept.py` (not renamed) also houses `synthesize_entity`, reusing its private claim-cleaning/citation helpers unmodified since `EntityMember`/`EntityClaim` share `ConceptMember`/`ConceptClaim`'s exact shape. `okf.py`/`okf_lint.py` (E9-E12)/`reconcile.py`/`canonicalize.run_delete_entry_stage` extend the concept treatment to `entities/` pages one-for-one (source pages gain a "## Entities mentioned" section mirroring "## Concepts covered", rendered by the same `render_source_with_concepts` call). `query.retrieve_entities` gates entities through the exact same `threshold` as items/concepts in `ask`/`stream_ask` — never an easier bar. `web/app.py` exposes `/entities` + `/entities/{id}` (read-only over the bundle, same pattern as `/concepts`). **No backfill**: existing entries simply have empty `entity_mentions`/no entity membership, which every surface (lint, web, query, export) already treats as the normal, ungrounded-in-error case — never reprocess an old entry to backfill entities.

- **External-collector queue: server half only (this phase).** YouTube's bot-identity refusal ("Sign in to confirm you're not a bot") is about this server's address, not any one video, and no server-side code can fix it (see the Phase 22/23 entries above) — the only remaining lever is fetching from a trusted machine elsewhere and handing the transcript back. This phase adds the queue that lets that happen later; it does not build the collector program or its UI. `web/jobs.py` gained a third lifecycle, fully disjoint from `queued`/`running` and `pending_fetch`/`fetching`: `STATUS_AWAITING_COLLECTION` (waiting) -> `STATUS_COLLECTING` (leased to a collector, with an expiry) -> `STATUS_QUEUED` (kind `KIND_YOUTUBE_STAGED`, once a transcript is submitted) — from there it's indistinguishable from a playlist prefetch and needs no further special-casing anywhere downstream. `distil.youtube.is_bot_check_refusal` recognizes YouTube's bot-identity challenge text — see the Phase 24 entry below for why this is a tolerant pattern match rather than a literal-substring one, and yt-dlp has no dedicated exception type/error code for this condition either way; an unrecognized future reword would just fall back to today's fail-immediately behavior, never mis-park an unrelated failure. `_distill_job` (single-video path) and `_fetch_playlist_video` (Fetcher path) are the only two call sites that check it, right where they already catch `YoutubeFetchError` — a non-bot-check failure (no captions, private, missing) is unchanged and still fails immediately. `JobStore.claim_for_collection` leases up to `limit` waiting jobs with a per-row guarded `UPDATE ... WHERE status=?` (the same idiom `claim_next_queued` already uses), so two collectors racing can never both claim the same video; `release_expired_leases` (a dead collector's lease lapsing) and `expire_stale_awaiting_collection` (nobody ever collects it — `collection_deadline`, set once on first entry and never reset by a lease claim/release, default 7 days via `DISTIL_COLLECTOR_EXPIRY_SECONDS`) both piggyback on `list_active()` exactly like `autoclear` already does, so the queue stays bounded purely from the existing `/jobs` Activity poll — no new background thread, and nothing to clean up on expiry since a job in this lifecycle never has a staged file yet (`kind` stays `"youtube"` until a real submit). `JobStore.submit_collected_transcript`/`report_uncollectable` are idempotent against a collector retrying after a lost HTTP response (already-queued/already-failed replies success again rather than erroring) via a status check before the guarded update. Auth is a second, independent credential (`DISTIL_COLLECTOR_TOKEN`, `web/auth.py`'s `request_is_collector_authorized`) — Bearer-only, ignores `is_public()`/localhost convenience entirely, and is checked inside the `/collector/*` routes themselves rather than `web/app.py`'s `_auth_gate` middleware (which exempts that path prefix from the owner check via `auth.path_is_collector`); it is never compared against `DISTIL_AUTH_SECRET`; see `tests/unit/test_web_collector.py` for the both-directions proof (collector token can't reach owner routes, owner token can't reach collector routes).

- **External-collector program (Helper 2, completes the queue PR #22 started).** `distil/collector.py` is the program that actually runs on the owner's machine: it claims one job at a time from `/collector/jobs/claim`, fetches it, and submits or reports it unfetchable — never more than one job leased at once, which is what "respect the lease" reduces to structurally rather than by configuration (`run_collector` always calls `client.claim(limit=1)`). It shares `distil/youtube.py`'s fetch core rather than reimplementing it: `youtube._fetch_captions_raw` (the same client chain, retry/backoff, and error surfacing `_fetch_into` already used) now backs two public entry points — `fetch_video_transcript` (parses into a `Transcript`, used server-side) and `fetch_raw_captions` (returns unparsed srt text, used by the collector, which hands it to the server's own `ingest_srt_text`-validated submit route rather than parsing locally — validated exactly once). `cookies_from_browser` (a yt-dlp `--cookies-from-browser` spec) is the collector's reason to exist — a signed-in browser session only means anything on a machine that has the browser — and `youtube._detect_browser_session` reports "signed_in"/"anonymous"/"unknown" per fetch via an `on_session` callback (mirrors `on_phase`'s shape) from a Netscape-format cookie jar yt-dlp exports alongside the fetch; it's a heuristic on Google's cookie names (`LOGIN_INFO`, `SAPISID`-family — present only when signed in), documented with the same confidence-bound honesty as `is_bot_check_refusal`, and the jar is read once and deleted immediately — cookie contents never appear in a log, an exception, or anything returned. Two retry layers stay separate on purpose: yt-dlp-level transient failures retry inside `youtube.py` as before; collector<->server HTTP transient failures (5xx, dropped connections) retry inside `collector.CollectorClient._request` with its own bounded backoff, and a retried `submit_transcript` is safe to resend verbatim because the server's `submit_collected_transcript` (PR #22) is already idempotent for exactly that case — proved in `tests/unit/test_collector.py` by an opener that fetches for real then raises as if the response were lost, confirming no duplicate/corrupted state. A permanent `YoutubeFetchError` (after `fetch_raw_captions`'s own retries are exhausted) reports through `/collector/jobs/{id}/unfetchable` instead of waiting out the 7-day `collection_deadline`. `CollectorClient` uses `urllib.request` only (no new runtime dependency — `distil/source.py` already uses it for the same reason); tests fake the whole HTTP boundary by wrapping a real `web.app.create_app()` `TestClient` behind an `opener(request, timeout)` adapter matching `urlopen`'s contract, so the wire format (query string, form-encoded body, Bearer header) is verified against the real routes, not a hand-rolled fake. CLI: `distil collector-run` (`distil/cli.py`), configured via `DISTIL_COLLECTOR_SERVER_URL`/`DISTIL_COLLECTOR_BROWSER`/`DISTIL_COLLECTOR_POLL_SECONDS`/`DISTIL_COLLECTOR_FETCH_PAUSE_SECONDS` plus the existing `DISTIL_COLLECTOR_TOKEN` (same credential PR #22 already scoped server-side); see `RUNBOOK.md` §10 for running it and starting it with the machine (a plain `launchd` plist on macOS — no installer framework). The collector reads/writes nothing else: no knowledge-base access, no other server route, and nothing the server sends it is ever executed — only a video URL in, caption text out.

- **Collector DNS resilience: ride out the owner's Mac's system resolver, never the server.** Observed repeatedly (always within a minute of a deploy): `getaddrinfo` fails for the server's hostname on the collector's machine while `dig`/`curl --resolve` both prove the name and the server are genuinely fine — the *system resolver's cache* is wrong, and fixing it needs `sudo`, which the collector must not have. `distil/collector_net.py`'s `open_with_dns_fallback` (the collector's default opener, wired into `CollectorClient.__init__` — existing tests are unaffected since they always pass an explicit `opener=`) always calls `resolve` (default `resolve_host`, a thin `socket.getaddrinfo` wrapper) first, on every single call; the last IP address a *real, completed* request most recently succeeded through is consulted only in the `except socket.gaierror` branch, via `DNSFallbackStore` (JSON file, default `~/.distil/collector_dns_cache.json`, override the directory with `DISTIL_COLLECTOR_STATE_DIR` — this is the collector's first piece of persistent state; a missing/corrupt file just means "no fallback yet"). TLS stays genuine throughout: `_PinnedHTTPConnection`/`_PinnedHTTPSConnection` substitute *only* the socket's destination address, by overriding `http.client.HTTPConnection`'s own `_create_connection` instance attribute rather than reimplementing `connect()` — SNI's `server_hostname`, the certificate check, and the HTTP `Host` header all stay the real hostname (`self.host`), inherited from the stdlib unmodified. Detection is by exception *type* (`socket.gaierror`), never by matching resolver error text — deliberately avoiding the exact defect class the Phase 24 entry above describes. Boundedness needs no extra logic: a failure connecting to the *fallback* address propagates as an ordinary `URLError`/`HTTPError` into `CollectorClient._request`'s pre-existing bounded retry/backoff and `run_collector`'s poll loop, and the very next call re-attempts real resolution from scratch (nothing here caches "give up on DNS") — so a dead cached address can never trap the loop while the real endpoint is reachable by name, and recovery back to normal resolution is automatic, never a restart. `tests/unit/test_collector_dns_resilience.py` proves all of this against a real local TLS server carrying a freshly-`openssl`-generated (never hand-typed) self-signed certificate — including that a hostname the collector *didn't* ask to pin to still fails certificate verification — with DNS failure simulated by a fake `resolve` that raises a genuine `socket.gaierror` for one specific hostname, never by stubbing the function under test.

- **Bot-check detection was silently inert for months; fixed by pattern-matching instead of literal-matching (Phase 24).** The original `_BOT_CHECK_MARKER` literal used a straight `'` apostrophe (`"...you're..."`), but YouTube's real refusal text uses the curly `’` (U+2019) apostrophe — confirmed from production failures on videos `AbpyqAfxZ8c`/`QER-0DaC-Gk`. The substring match therefore matched nothing, ever, in production: every bot-checked video failed outright instead of being parked in the collector queue PR #22/Helper 2 built. The original tests couldn't catch this because their fixture was hand-typed with the same straight quote as the implementation — test and bug shared one wrong assumption. Fixed two ways, both in `distil/youtube.py`: (1) `_BOT_CHECK_RE` replaces the literal with a regex matching the stable, low-punctuation core of the sentence (`"sign in to confirm you" + 0-2 arbitrary chars + "re not a bot"`, case-insensitive) so straight/curly/other apostrophe variants — or a future reword that keeps that shape — all match without risking another single-character miss; see its surrounding comment for the full reasoning, and `tests/unit/test_youtube.py`'s `_REAL_BOT_CHECK_STDERR` (genuine captured text, curly apostrophe byte-for-byte) for the regression proof. (2) Because a dead detector and "nothing needed it" look identical from outside, `PotDiagnostic.bot_check_detected` (surfaced by the same `distil youtube-diagnose-pot`/`GET /diagnostics/youtube-pot` diagnostic PR #20 built) now reports whether `is_bot_check_refusal` recognizes a given diagnostic run's own output — run it against a video you know is bot-checked to confirm detection is actually alive, rather than inferring liveness from silence. Audited the codebase for the same defect class (hand-typed literal vs. external-tool prose output): `_TRANSIENT_MARKERS` (429/5xx retry detection) also matches external `yt-dlp`/HTTP output by literal string, but those are standardized RFC reason phrases (`"Too Many Requests"`, `"Bad Gateway"`, ...) with no apostrophes or typographic-restyling risk, and `_detect_browser_session`'s cookie-name matching (`LOGIN_INFO`/`SAPISID`) is structural, not prose — neither is the same class of bug, and neither was changed.

- **Waiting-for-collector state is a first-class, explanatory presence in the web UI, not a silent gap (Helper 3).** Phase 24 fixed bot-check *detection*, but the web Activity view's status map still had no entry for `awaiting_collection`/`collecting` — a parked video rendered as "Unknown" and dropped out of live polling, which looked exactly like the app being broken. All badge/wording/staleness decisions live server-side in `web/jobs.py`, not in template JS: `status_presentation(status)` (backed by the one `_STATUS_PRESENTATION` map covering every status, including these two) returns each job's badge class/text/spinner and whether it should keep the Activity view polling; `collector_status_for_job(job, last_checkin_iso)` returns the owner-facing explanation (why it's parked, how long until `collection_deadline` gives up, and — the part most worth getting right — whether anything is actually coming). That last part needed a signal the server didn't have: `JobStore.record_collector_checkin()`/`last_collector_checkin()` (a one-row `collector_meta` table) records every authenticated `/collector/jobs/claim` call, *even an empty one* — an empty claim still proves the collector process is alive and polling, which is what makes it trustworthy as an "is anything coming" signal rather than only firing when there happens to be work. `GET /jobs` attaches this timestamp plus the computed `presentation`/`collector_status` dicts to every job dict (still a bare array, not reshaped into an object); `web/templates/index.html`'s `jobBadge`/`collectorDetail` are thin renderers of those already-computed values, and the live-poll check is `job.presentation.live` rather than a separate client-side status set. A status past `COLLECTOR_STALE_SECONDS` (5 min, in `web/jobs.py`) reads as "nothing is currently collecting" rather than a hopeful, unresolving "waiting". `remove_queued` also accepts `AWAITING_COLLECTION` (never `COLLECTING`, which has a lease a collector may be mid-fetch against) so a parked video can be given up on like any other queued one. None of this touches the parking rules, bot-check detection, or the collector HTTP protocol — it's presentation (now server-computed) and an additive, read-only liveness signal on top of them.

- **Narrative summary layer (additive, beside the grounded note) + a general per-stage model resolver.** `distil/note.py`'s note is built only from extracted `KnowledgeItem`s, so its depth is capped by what triage/extraction happened to keep as discrete claims — it never sees the transcript. `distil/summary.py` fixes that by reading the transcript directly: `chunk_transcript_text` splits on sentence boundaries (never mid-sentence) into ~`DISTIL_SUMMARY_CHUNK_CHARS` (default 12,000 chars, ~15-20 min of speech) pieces, each summarized, then merged into one flowing account via `synthesize_narrative_summary`. Both the per-chunk and merge completions go through one shared retry loop (`_complete_with_coverage_retry`) that treats a too-thin result (scaled floor: `max(40, ratio * source_len)`) and a dropped connection as the same retryable failure, bounded by `DISTIL_SUMMARY_MAX_RETRIES` (default 3) — exhausting it raises `NarrativeSummaryError` rather than ever returning or persisting a thin result. `models.NarrativeSummary` (`KBEntry.narrative_summary`, optional) carries no citations by design — it's the readable account to read first, not the grounded structure to trust and check (that's still `DistilledNote`, unmodified). `pipeline.run_pipeline`'s narrative-summary stage is additive and opt-in: it only runs when a caller passes `summary_client` *and* `config.enable_narrative_summary` (default `True`); omitting `summary_client` (every pre-existing caller) reproduces prior behavior exactly, and a failure inside the stage is caught and logged, never allowed to turn a would-have-succeeded filing into a failed one. Model selection for this (and every other LLM-calling stage) goes through `distil/model_config.py`'s `resolve_stage_model(stage)` — a **general per-stage mechanism**, not a one-off second global variable: `DISTIL_MODEL_<STAGE>` overrides that stage only (`triage`/`extract`/`link`/`note`/`graph`/`canonicalize` fall back to the existing `DISTIL_MODEL`; `summary` falls back to a hardcoded Haiku-tier default instead, since summarizing is compression, not judgement — extraction/triage/note/concepts/entities all stay on the strong model, unchanged). `run_pipeline` grew matching optional `triage_client`/`extract_client`/`link_client`/`note_client`/`graph_client`/`canonicalize_client` kwargs (each defaulting to `None`, meaning "use the shared `client`" — today's exact behavior); no caller passes them yet, so today's model selection for those six stages is unchanged byte-for-byte. Wiring `cli.py`/`web/app.py` to actually pass distinct per-stage clients, and any settings UI for editing `DISTIL_MODEL_<STAGE>` values, are deliberate follow-ups — the mechanism existing now is what makes a later stage-specific model change configuration, not code. **Per-entry refresh** (`distil/refresh_summary.py`, `distil refresh-summary <id>` / `POST /entries/{id}/refresh-summary`) regenerates *only* `narrative_summary` from the entry's already-stored `okf/raw/<slug>.md` page (`okf.load_raw_transcript_text`) — never re-fetches, never re-extracts, and `store.file_entry(entry)` with no `transcript=` kwarg (the pre-existing "feedback-only re-file" path) is what keeps items/concepts/entities/OKF pages untouched. An entry with no stored raw page (filed before OKF export existed, or reconciled away) reports that plainly rather than offering a doomed retry.
